# ADR 0002 · GTFS as primary data source, synthetic timetable as fallback

**Status:** Accepted (2026-10-10) · refined by [ADR 0004](0004-gtfs-dataset-format-and-refresh.md) (per-route fallback, format, refresh schedule, datasets not committed)

## Context

The simulator synthesises timetables from service-level summaries (trips per time band, first/last run) because no stop-by-stop timetable was available. The Comune di Milano now publishes an **official GTFS Schedule feed** generated by AMAT from ATM's planned service:

- dataset: [ds929 – Orari del trasporto pubblico locale nel Comune di Milano in formato GTFS](https://dati.comune.milano.it/dataset/ds929-orari-del-trasporto-pubblico-locale-nel-comune-di-milano-in-formato-gtfs), licence **CC BY**, direct link `https://dati.comune.milano.it/gtfs.zip`;
- verified on 2026-10-10 through the portal's catalogue metadata and the Mobility Database page (the zip itself was not downloaded from the development workspace): resource `ds929_gtfs.zip`, 60.3 MB, last modified 2026-09-21, update frequency *biweekly* (the portal notes two weeks to one month);
- the [Mobility Database](https://mobilitydatabase.org/feeds/gtfs/mdb-2666) lists it as an official feed with **no validation errors**, 166 routes of type **tram, metro and bus**, and these features: route colours, **shapes**, headsigns, transfers, feed info, stop wheelchair accessibility;
- each release covers ~4–5 weeks of service (latest: 14 Sep – 19 Oct 2026) and past releases weighed ~260–770 MB unzipped.

ATM does not publish GTFS-Realtime as open data, so positions remain simulated — but from real planned times instead of evenly spaced trains.

## Decision

1. GTFS becomes the **primary source** for stops, routes, shapes and timetables of metro and surface lines.
2. The current synthetic scheduler stays as **fallback** when the current date is outside the feed's validity (or the dataset fails to load), with a visible notice stating the data vintage.
3. A **scheduled GitHub Actions workflow** downloads the feed, rebuilds the compact datasets and redeploys (weekly on purpose — twice the publication rate, so a new release is picked up within days — plus manual trigger). GitHub runners download the feed; nothing is fetched by the browser from the city portal at run time.
4. The pipeline (Python standard library only, as today) streams `stop_times.txt` and emits a compact format: patterns (stop sequences), shared time profiles, trips as `(pattern, profile, start, service)`, calendars expanded to service dates in a rolling window, simplified shapes. A test enforces a size budget.
5. Attribution "Comune di Milano / AMAT – CC BY" is shown in the app and in the README.

## Consequences

- Removes the main limitations listed in TECHNICAL_DESIGN §7: even spacing, assumed band boundaries, branch patterns, distance-based running times, straight-line surface geometry.
- The topology of the metro (branches, station order) is derived from the feed; the hand-written builder becomes a cross-check test (same stations, same branch junctions).
- New failure mode: a feed release can be late or malformed. The workflow keeps the last good dataset if validation fails, and the app falls back to the synthetic timetable when the window has expired.
- Raw downloads stay git-ignored; generated datasets are committed by the workflow (or published as a release asset if they exceed a size that makes the history heavy — decided in F1 with real numbers).
- The surface stop ids used today (`id_amat`) must be mapped to GTFS `stop_id`s; verified in F1 on a real feed.
